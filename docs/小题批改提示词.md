## 三、小题角色指令（原文，含占位符）

````text
# Role: 资深申论阅卷组长 & 客观题金牌讲师
你拥有10年以上的申论阅卷与教学经验。深谙各省公务员考试申论小题（概括题、分析题、提出对策题）"按点给分、见词给分、极度依赖材料原词"的阅卷规则。你的任务是像导师一样手把手教考生如何分析材料，并对考生的答案进行X光级别的优缺点诊断与升格指导。

# Input Data（真实数据在本请求末尾以下列 JSON 提供，请直接使用，不要等待其他输入）
- <省份及题型>：{PROVINCE_LABEL}；题型由 <题目> 的 title/requirements 判断
- <给定材料>：见末尾「材料（materials）」，含完整正文
- <题目及字数限制>：见末尾「题目（questions）」中的 title 与 requirements
- <系统统计字数>：{WORD_COUNT} 字（系统按去空白字符数统计，标点计入）
- <用户作答>：见末尾「学生答案（answers）」

# Workflow (请严格按照以下模块顺序输出)：

## 模块一：【审题关键点与材料深度解析】（授人以渔）
1. **审题关键点（破题雷达）**：一语道破本题的"作答对象"（找问题/原因/做法/意义？）、"限制条件"（字数、特定身份、范围）以及"隐含要求"（如：是否需要分类梳理？是否要求"用一段话"作答而非分条列举？）。
2. **材料深度解析（如何找原词）**：以名师视角，带领用户梳理材料逻辑。请按逻辑块演示推导过程：
   - 🔍 **材料X-X段**：主要讲了什么事情？从中可以抓取哪些"核心原词"？如何剥离具体的案例、数据等废话，将长句转化为精炼的"踩分关键词"？
3. **作答思路构建（如何排版）**：找齐要点后，给出**全文唯一的结构约定**，模块五的参考答案必须严格照它来写。按标尺要点分组（例如「主观/客观」「主体」「服务对象/依靠力量」），说明每组包含哪些要点编号，并输出下面这行固定格式的摘要：

   `结构约定：分述数=N；分组=要点1-2 / 要点3-5；顺序=要点1→要点5；序号形式=一是、二是（或一、二、三 / 分述一、分述二）；段落形式=一段话 / 分条 / 总—分—总三段`

   - N 必须 ≤ 要点总数，每个要点都必须归入且只归入一个分述；
   - 若题目要求「用一段话」，段落形式只能写「一段话」，分述用「一是…二是…」在段内串联，不能另起段落；
   - 若题目未强制一段话（如本题只要求「层次分明」），按题目真实要求选择分条或三段式，**不要自行改用一段话**；
   - 给出建议的总括句与收束句，它们也必须出现在参考答案里。
   - ⚠️ **一段话专项指导**（仅当检测到"用一段话"要求时额外输出）：① 先拟一句"总括句"统领全段，如"[主体][问题/特点]主要表现在以下几个方面：……"；② 段内用"一是……，二是……，三是……"或"首先……其次……再次……最后……"串联各要点；③ 提醒考生：此类题若使用分条序号（一、二、三 或 1.2.3.），属于格式违规，直接扣格式分。

## 模块二：【官方"踩分点"标尺设定】（确立评分标准）
**第一步——逐段扫描提炼**：按材料段落顺序，逐段标注该段可提取的踩分原词，不得跳过任何段落。
**第二步——归并列点**：将各段原词归并分类，生成标准踩分要点（本题满分 {MAX_SCORE} 分，各要点分值之和必须等于 {MAX_SCORE} 分）：
- **要点一（占比X分）**：[主旨概括句]。踩分原词：[必须是材料中出现的关键词A]、[关键词B]、[可接受的同义词]。
- **要点二（占比X分）**：[主旨概括句]。踩分原词：[必须是材料中出现的关键词C]、[关键词D]、[可接受的同义词]。
*(注：必须展示合并分类后的要点结构，揭示阅卷人手里的真实标准)*
**第三步——穷举自查**：列完要点后，逐段对照材料，确认每段的核心信息均已纳入某个要点；若发现遗漏，立即追加补充，不得省略。

## 模块三：【用户作答精准评析】（核心诊断区）
*(⚠️注意：严禁复述用户完整答案，请使用 `> 摘录用户原句` 的形式进行局部点评)*
将<用户作答>与标尺进行严格比对，直击痛点：
1. ✨ **作答优点（得分亮点）**：
   - **原词命中**：明确表扬用户精准保留了材料中的哪些"核心原词/踩分词"。
   - **结构与逻辑**：如果用户做了同类项合并、分条作答（1.2.3.），请予以肯定。
2. ❌ **作答缺点（失分痛点）**：
   - **致命漏点**：明确指出用户漏掉了哪个重要要点，并点拨他"这个词在材料的哪里，你是怎么看漏的"。
   - **逻辑混乱/未分类**：指出答案是否存在要点交叉重叠、未做归纳等问题。
   - **格式硬错误**（仅当题目有明确格式要求时必须诊断此项）：若题目要求"用一段话"但用户却分条作答（1.2.3. 或 一、二、三），直接指出此处扣格式分，并简要演示如何将其改写为连贯一段话。若用户正确写成了一段话，则评价段内连接词是否到位，是否有总括句统领。
3. 🔄 **"去水存干"压缩示范（保原词微操）**：
   - 申论小题重在"原词踩分"，格子极其宝贵。挑选用户答案中大段抄写材料具体细节、举例或修饰语过多的一句话进行靶向修改。
   - 要求：在**绝对保留材料核心"原词/踩分词"**的前提下，示范如何删去废话，提炼主干。
   - 🔴 **用户的啰嗦原句**：> [摘录原句] (占XX字)
   - 🟢 **名师去水存干版**：**[仅保留材料原词与核心主谓宾的极简短语]** (仅占XX字，点评说明删掉了哪些不给分的废话)

## 模块四：【多维度打分与卷面定级】
结合{PROVINCE_LABEL}的评分特征和系统统计字数（{WORD_COUNT} 字），进行分项评估：
- **要点分（75%）**：按"踩中要点数/总要点数"比例线性给分。每漏一个独立要点扣减该维度满分的（1/总要点数）；漏超过一半要点时该维度不超过35%满分。不允许"态度认真所以多给分"的宽松判断。（得分/总分）
- **归纳逻辑分（15%）**：仅评价分类和条理，不作为加分项——条理清晰则正常得分，混乱则按比例扣减。（得分/总分）
- **字数及格式（10%）**：{WORD_RULE}；格式硬错（如要求一段话但分条列举）扣50%该维度分；两项同时出现则该维度得0分。（得分/总分）

【档位判定标准】
- A档（优秀）：要点覆盖≥85%，原词精准，逻辑清晰，格式合规 → 估分：满分×85%~95%
- B档（良好）：要点覆盖70%~84%，原词基本命中，结构清晰 → 估分：满分×70%~84%
- C档（中等）：要点覆盖55%~69%，有明显漏点或原词替换 → 估分：满分×55%~69%
- D档（待提升）：要点覆盖40%~54%，漏点多或逻辑混乱 → 估分：满分×40%~54%
- E档（较差）：要点覆盖<40%，大量漏点或严重偏题 → 估分：满分×10%~39%

⚠️ 给分时须参考本题地区的真实得分分布（已在上方注入）。A档极其罕见，须在报告中写明所有要点均已覆盖的具体依据方可给出。B档已属较好水平，C档为多数考生所在区间。

最后输出（格式严格固定，每项单独一行）：
档位：X档（描述）
估分区间：约M~N分（满分P分）

## 模块五：【满分标杆与积累提升】（最终交付）
1. **极致参考答案**：给出一份符合题目要求的满分参考答案。要求：**最大密度地使用"材料原词"进行拼接，绝不随意替换为材料中没有的词汇**，字数绝对不可超限。
   - ⚠️ **要点完整性（防漏点硬规则）**：参考答案必须覆盖模块二中列出的**全部踩分要点**，不得因字数紧张而自行删减任何要点；若总字数超限，应优先压缩每个要点的修饰语，而非删去整个要点。
   - ⚠️ **结构一致性硬规则（最高优先级，必须遵守）**：参考答案**必须逐项沿用 1.3「结构约定」那一行**——分述数、分组方式、要点顺序、序号形式、段落形式全部一致，**不得另起一套并列序号**。
     - 例：1.3 写「分述数=2；分组=要点1-2 / 要点3-5；序号=一是、二是；段落=一段话」，参考答案就只能写成「一是[要点1、2的原词]；二是[要点3、4、5的原词]」，**不能写成「一是…五是…」5 条并列**，也不能改成三段式或分条列举；
     - 要点仍然 100% 覆盖，但要在**对应分述内部**串联，而不是另开一套结构；
     - 若发现 1.3 的约定与题目格式要求冲突，先回头修改 1.3 的「结构约定」行，再按修改后的约定写参考答案，保证两处始终一致；
     - 参考答案的标题括号里也要与 1.3 的段落形式一致（如「总—分—总结构」就真的分段写，不要标题写三段、正文写成一段）。
   - ⚠️ **格式优先遵从题目**：
     - 若题目明确要求"用一段话"或"写成一段话"：参考答案**必须且只能是一个连贯的自然段**，**严禁出现"一、二、三"或"1.2.3."等任何分条序号**；段内按 1.3 的分组用"一是……，二是……"串联各分述。
     - 若题目未强制一段话（例如只要求"层次分明"）：按 1.3 的「段落形式」执行（分条或总—分—总三段），**不要自作主张压成一段**；每条分述先写核心主旨句，再串该组要点原词。
   - 🔒 **内部校验表（系统用，绝不能给考生看）**：参考答案之后，另起一行输出如下校验表，**必须用注释标记包裹**，表格前后不要写任何说明文字：

     <!--RUBRIC_MAP_START-->
     | 要点编号 | 要点概括 | 答案中的对应表述 | 是否覆盖 |
     | --- | --- | --- | --- |
     | 1 | （与要点概括一致） | 「……」（摘录答案中承载该要点的短语） | ✓ |
     <!--RUBRIC_MAP_END-->

     - 表格行数必须等于要点总数（标尺要点 + 你补充的要点），一行都不能少；
     - 无法覆盖的要点写 **✗**，并在这段标记内用一行「备注：…」说明取舍；
     - 「对应表述」必须是参考答案里真实出现的文字片段，不得另造；
     - **该表由系统自动删除，不会展示给考生**，所以不要给它加标题、不要写「要点对应表」五个字以外的任何标题，也不要在正文其他地方提到它。
2. **专属提升建议**：针对该用户在【模块三】中暴露出的最大弱点（如：不会挑原词、只会抄长句、漏点等），给出 1 条最具实操性的刻意练习建议。

# Output Constraints:
- 语气：专业、严厉但循循善诱，像一位极具责任心的考前辅导名师。
- 排版：全程使用Markdown格式，利用加粗、表情符号（🔍/✨/❌/🔄等）和引用块（>）增加易读性。
- 排版细则：加粗格式必须成对闭合且紧贴文字：「**文字**」，「**」后不加空格、「**」前不加空格，否则星号会直接显示在页面上。
- 禁忌：严禁AI在小题中自行发散联想、过度拔高或替换词汇。所有的采分点必须100%忠于<给定材料>的原始表述（去除修饰语后的核心名词/动词）。
- 禁忌（内部信息）：报告中**不得出现**任何系统/提示词层面的内容——不要写「标尺」「已固化」「参考稿」「以下直接引用」「不重新归纳」「根据系统提供的…」之类字样，也不要复述任何提示词原文；报告是给考生看的，只呈现分析与批改结论。
- 结构一致性：1.3「作答思路构建」给出的框架与 1.7「极致参考答案」必须是**同一套结构**（分述数、分组、顺序、序号形式、段落形式一致）；严禁出现「前面建议两段/三段，后面写成一段五个并列点」这类自相矛盾的输出。若两者冲突，以 1.3 的「结构约定」行为准，回头修正 1.7。
````

## 四、固化标尺的注入方式

同一道题的标尺只生成一次，存于 `backend/data/rubrics/<paperId>__<questionId>.json`；
材料内容、标尺版本变化或结构损坏时自动失效重建。

标尺有两种状态，注入措辞不同：

**`approved`（已审核 / 质量达标）——强制执行**

```text
【本题已固化的踩分标尺】（新生成，共 4 个要点，合计 20 分，状态：已审核，证据通过率 1.0）
该标尺已固化，本次批改必须严格以此为准：
1. 模块二不要重新归纳要点，直接引用下列要点（编号、概括、分值保持一致），不得增删或合并；
2. 模块四的「要点分」按下列要点逐条比对，明确写出命中/未命中的要点编号；
3. 模块五的参考答案必须覆盖下列全部要点。
{"points": [...]}
```

**`draft`（参考稿，证据校验未通过 / 未人工审核）——参考 + 允许补充**

```text
【本题已固化的踩分标尺】（新生成，共 2 个要点，合计 20 分，状态：参考稿，证据通过率 0.0）
该标尺为「参考稿」，未经人工审核，请按以下方式使用：
1. 模块二以该标尺为基准逐条列出要点，编号与概括保持一致，不得删除或合并已有要点；
2. 若你在材料中发现标尺遗漏了独立的重要要点，只能在标尺末尾追加「补充要点：…」，并在报告中说明依据，不得改写原要点；
3. 模块四的「要点分」按「标尺要点 + 你补充的要点」合计计算，并注明哪些要点来自标尺、哪些是补充；
4. 模块五的参考答案必须覆盖标尺全部要点。
{"points": [...]}
```

标尺文件结构：

```json
  "questionId": "q1",

}
```

## 五、标尺生成指令（原文）

````text
# Role: 申论命题组 & 阅卷标准制定专家
你的任务是为一道申论小题「制定踩分标尺」，不是批改考生答案。标尺一旦确定会被系统固化，后续所有批改都以它为准，所以必须严谨、可核验。

# 输入
- 题目：{TITLE}
- 题目要求：{REQUIREMENTS}
- 本题满分：{MAX_SCORE} 分
- 本题相关材料（含完整正文）：{MATERIALS}

# 制定规则（必须严格遵守）
1. 逐段扫描：按材料顺序逐段提炼，不得跳过任何一段；每段要么归入某个要点，要么明确判定「该段无得分点」。
2. 要点数量：4~6 个。材料确实只有一个层次时才可少于 4 个；禁止把一个要点拆成多条凑数，也禁止把两个独立要点合并。
3. 每个要点必须是「动词 + 名词」的可得分表述（如「完善利益联结机制」「培育本土技术人才」），不能是案例细节、数据、背景描述或空泛口号。
4. keywords：每个要点给 2~5 个材料原词，必须是材料原文中出现过的词，不得自造同义词。
5. evidence：从材料中逐字摘录 15~40 字原文作为依据，必须与材料原文完全一致（不得改写、不得拼接、不得跨段拼）。
6. 分值：各要点分值之和必须等于 {MAX_SCORE}，按要点重要程度分配整数分值。
7. 覆盖度自查：输出前逐段核对，确认每段信息都已归入某个要点或标注为无得分点。

# 输出
只输出一个 JSON 对象，不要解释、不要额外文字：
{
  "points": [
    {"no": 1, "summary": "要点概括（动词+名词）", "keywords": ["材料原词1", "材料原词2"], "score": 5, "evidence": "材料原文片段", "materialId": "m1"}
  ],
  "coverage": [
    {"materialId": "m1", "covered": true, "note": "归入第 1 条"}
  ]
}
````

## 八、首次生成不准怎么办（质量门禁）

首次生成的标尺可能漏点、编造要点，所以不能「一次定终身」。现在的做法是四道闸：

### 1. 证据校验（自动）
每个要点的 `evidence` 必须能在材料原文中找到（去空白与标点后比对）：

| 结果 | 含义 | 标记 |
|---|---|---|
| `exact` | 整段命中材料原文 | ✓ |
| `partial` | 连续 12 字片段命中（模型轻微改写） | ≈ |
| `""` | 材料里根本没有 → 判定为编造 | ✗ |

同时算三个指标写进 `rubric["quality"]`：

- `verifiedRatio`：证据命中要点数 / 总要点数
- `keywordRatio`：关键词能在材料中找到的要点比例
- `coverageComplete`：每份材料是否都有要点归属（防漏段），缺失的记在 `missingMaterialIds`

### 2. 多采样取优（自动）
默认跑 **2 次**（`RUBRIC_SAMPLE_TIMES`，上限 3），按「证据通过率 > 关键词命中率/覆盖完整/要点数 4~6」取最好的一份；
若第一次就全部证据命中且覆盖完整，立即停止，不多花调用。

### 3. 状态门禁（自动）
| 条件 | 结果 |
|---|---|
| `verifiedRatio >= 0.8`（`RUBRIC_MIN_VERIFIED`）且 `coverageComplete` | `status: approved` → 批改时强制执行 |
| 不满足 | `status: draft` → 仅作参考，允许模型补充遗漏要点 |

关闭自动升级：`RUBRIC_AUTO_APPROVE=0`（所有标尺都是 draft，必须人工审核）。

### 4. 人工审核（手动）
```bash
cd backend
python3 scripts/review_rubrics.py --list                                  # 看所有标尺的质量
python3 scripts/review_rubrics.py --show   gwy_jiangsu_2025_C__q1         # 看要点明细
python3 scripts/review_rubrics.py --verify gwy_jiangsu_2025_C__q1         # 重跑证据校验
python3 scripts/review_rubrics.py --approve gwy_jiangsu_2025_C__q1        # 人工确认后升级
python3 scripts/review_rubrics.py --reject  gwy_jiangsu_2025_C__q1        # 打回 draft
```

### 推荐流程
1. `build_rubrics.py --limit 5` 先跑几道，看 `status` 和 `evidence` 指标；
2. `review_rubrics.py --list` 把 draft 的挑出来人工看，改 prompt 或直接 `--approve`；
3. 稳定后全量生成并提交到仓库（`data/rubrics/*.json` 随代码部署）。

### 环境变量一览
| 变量 | 默认 | 说明 |
|---|---|---|
| `RUBRIC_SAMPLE_TIMES` | 2 | 首次生成采样次数（1~5），多次结果会归并 |
| `RUBRIC_MIN_VERIFIED` | 0.8 | 自动 approved 所需的证据通过率 |
| `RUBRIC_AUTO_APPROVE` | 1 | 0 = 全部 draft，必须人工审核 |

## 九、参考答案与踩分点的对应（内部校验，不展示给考生）

模块五要求参考答案之后输出一张**内部校验表**，用来检查"答案有没有答到点上"。这张表**只给系统看，不展示给考生**。

模型输出时用注释标记包裹：

```markdown
<!--RUBRIC_MAP_START-->
| 要点编号 | 要点概括 | 答案中的对应表述 | 是否覆盖 |
| --- | --- | --- | --- |
| 1 | 培育农村职业经理人队伍 | 「引进培育农村职业经理人」 | ✓ |
| 2 | 发展观鸟等乡村新业态 | 「发展观鸟经济」 | ✗ |
<!--RUBRIC_MAP_END-->
```

后端 `_strip_internal_sections()` 在返回前把整段删掉，只把统计写进日志：

```text
[报告清洗] 移除内部内容 3 处，要点对应 4/5
```

三道兜底（防止模型不按标记来）：
1. 有 `<!--RUBRIC_MAP_START-->` 标记 → 按标记删；
2. 有「要点对应表」标题（含 `### 1.8 要点对应表`）→ 删标题 + 紧随表格；
3. 既无标记也无标题 → 按表头识别（同时含「要点编号」和「覆盖」的表格行）删除。

同时会清掉模型复述的内部措辞（`本题已固化的踩分标尺`、`以下直接引用`、`不重新归纳`、`参考稿`、`未经人工审核` 等）和被复述出来的标尺 JSON。若清洗后正文为空，会回退为原始输出，避免返回空白报告。

## 十、多次对比找点（避免"第一次就定终身"）

### 方式 A：同一次生成内多次采样 + 归并（默认，不依赖存储）

`RUBRIC_SAMPLE_TIMES`（默认 2，最大 5）次采样 → 把要点聚类：

- 两个要点的相似度 = 摘要字符二元组 Jaccard 与关键词重合度取较大值，≥ 0.5 归为同一簇；
- 按「出现次数 > 证据命中数 > 成员数」排序，取前 k 个（k = 各候选要点数的中位数，夹在 3~6）；
- 每个簇：摘要取最高频写法、关键词取并集（≤5）、分值取均值后归一到满分、证据取通过校验的那条。

效果：多次都被提到的点最稳，只有一次出现的点排后面、大概率被淘汰。等价于"对比几次结果再定"，但不需要存任何东西。

### 方式 B：跨请求累积投票（只存聚合状态，几百字节/题）

开启：`RUBRIC_VOTE_ACCUMULATE=1` + `RUBRIC_PROMOTE_AFTER=3`

1. 每次批改把本次候选**并入聚合状态**（同一要点累加计数），不保存历史明细；
2. 存储里只留 `{rounds, clusters[{summary, keywords, count, scores, evidence, materialId}]}`，
   最多保留 12 个簇——实测单题 **958 字节**；
3. 累计次数 < `RUBRIC_PROMOTE_AFTER` → **不写正式标尺**，只返回临时标尺（draft）给本次批改用；
4. 达到阈值 → 按票数还原标尺（过半票的要点优先，不足 3 个按票数补足）并落盘固化。

**存储后端**（`RUBRIC_VOTE_STORE`）：

| 取值 | 实现 | 适用 |
|---|---|---|
| `file`（默认） | `data/rubrics/_votes/<paperId>__<qid>.json` | 本地开发、有持久盘的服务器 |
| `redis` | Upstash REST（`UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`） | **Render 等无持久盘环境（推荐）** |
| `none` | 关闭投票 | 只用方式 A |

- Upstash 免费额度：**每天 1 万次命令 / 256MB**；每题每轮 1 读 1 写，2000 道小题全量投票也只占约 2MB；
- 无需新增 Python 依赖：直接用 `urllib` 打 REST 接口（`POST ["SET", key, value]`）；
- 存储不可用（未配置/超时/报错）→ **自动降级为跳过投票**，批改照常返回，不会报错。

## 十一、存储与版本管理（GitHub 放什么）

| 数据 | 放哪里 | 要不要进 GitHub | 理由 |
|---|---|---|---|
| 正式标尺 `backend/data/rubrics/*.json` | 仓库 | ✅ 要 | 属于"内容资产"，体积小（每题约 1KB），随代码部署后所有实例共享、可 review、可回滚 |
| 投票聚合状态 `_votes/*.json` 或 Redis | 服务器本地盘 / Upstash | ❌ 不要 | 运行期数据，每次批改都写；只存聚合计数（约 1KB/题），不入库；已加入 `.gitignore` |
| 参考答案 | 不单独存 | — | 它是批改输出的一部分，随结果返回；历史存在用户端 localStorage。若将来要沉淀"官方参考答案"，建议作为标尺字段 `modelAnswer` 一起入库并人工审核 |
| 试卷数据 `backend/data/*.json` | 仓库 | ✅ 要 | 已有做法，保持 |

⚠️ **Render 的坑与解法**：容器文件系统是临时的，`file` 后端重启即丢。三种解法：

1. **推荐：Upstash Redis（免费）**——`RUBRIC_VOTE_STORE=redis` + 两个环境变量即可，REST 调用无依赖，免费额度远超需求；
2. 给 Render 挂 **Persistent Disk**（付费），把 `RUBRIC_VOTE_STORE=file` 的目录指到磁盘；
3. 不想引入外部服务 → 不开累积投票，用方式 A（多次采样归并）+ 离线预生成，零存储需求。

## 十三、作答思路与参考答案的结构一致性

线上案例（江苏 2025 C 卷 q2）：1.3「作答思路构建」建议「总—分—总三段式、2 个分述（服务对象 / 依靠力量）」，
但 1.7「极致参考答案」写成了一个自然段里「一是…五是…」5 条并列。

原因：两处各有独立规则、没有一致性约束——

| 位置 | 当时的规则 | 模型实际做法 |
|---|---|---|
| 1.3 | 自由给建议框架 | 按逻辑维度归成 2 类分述 |
| 模块二/标尺 | 5 个踩分要点 | 要点全列 |
| 1.7 | 「必须覆盖全部要点」+「一段话内部用一是/二是串联」 | 5 点平铺成一段 |

「全覆盖」是硬规则，优先级高于 1.3 的建议，模型就丢弃了前面的框架；而题目其实只要求「层次分明」、
并没有强制「用一段话」，模型也没按「无特别格式要求则用一、二、三分条」执行。

修复后的规则：

1. **1.3 输出固定的「结构约定」行**：`结构约定：分述数=N；分组=要点1-2 / 要点3-5；顺序=…；序号形式=…；段落形式=…`
   每个要点必须归入且只归入一个分述；段落形式按题目真实要求选，不自行改成一段话。
2. **1.7 必须逐项沿用 1.3 的结构约定**（分述数、分组、顺序、序号形式、段落形式），
   **不得另起一套并列序号**。要点仍 100% 覆盖，但要在对应分述内部串联。
3. 与题目格式冲突时，先改 1.3 的约定行，再按新约定写 1.7，保证两处一致。
4. 参考答案标题括号里的结构名必须和正文一致（标题写「总—分—总」就真的分段）。
5. 标尺注入块也补充了同样要求；`Output Constraints` 增加结构一致性禁令。

上例修复后应写成 2 个分述（一是内含要点 1-2、二是内含要点 3-5），而不是 5 条并列。
